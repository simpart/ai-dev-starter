# PROJECT 共通基準

> 状態: v1.0（2026-11-04）
> 本書は、生成先プロジェクトの PROJECT.md が **満たすべき状態** を定義する。生成時の目標と、レビュー時の判定基準の両方に、同じ基準を使う。
> AI の作業手順は扱わない。また、本書は章立てのテンプレートではない。

---

## 0. 本書の適用

本書は、プロジェクト固有の PROJECT.md の新規生成・レビュー・更新に適用する。依頼された作業に応じて、本書の該当する基準を適用する。ユーザーの個別の指示によって、本書の品質基準が無効になることはない。

本書を参照して PROJECT.md の生成・更新を依頼された場合は、追加の詳細な指示がなくても、次を満たす成果物を提供する。

- 最終的に合意された事項が正確に反映されていること（K6）。
- 7.2 の要修正が0件であること。
- PROJECT に含めなかった重要な決定事項・検討事項がある場合は、成果物とは別に報告されていること。
- 重大な未決定事項が残る場合は、その内容と、後続の設計・開発への影響が明示されていること（6.3）。

章立てと分量は固定せず、プロジェクトの規模・性質・成熟度に合わせる。本書は、AI の作業の順序、使うツール、レビュー・修正の進め方を定めない。

## 1. PROJECT の目的と責務

### 1.1 目的

PROJECT は、プロジェクトの目的・提供価値・基本方針・制約を明確にし、**後続の設計・実装で「これはやるべきか／やってよいか」を判断する基準**を与える文書である。
プロジェクトの概要や機能の一覧ではない。開発が進んでも目的と方針を見失わないための文書であり、詳細を蓄積する場所ではない。

主な読者は、機能を提案・実装する AI エージェントと、新しく加わる人間である。

### 1.2 判断テスト

任意の新機能・変更案について、PROJECT から次の問いに答えられること。

1. プロジェクトの目的に合致するか
2. 対象者の課題解決につながるか
3. 提供価値を高めるか（機能が増えるだけになっていないか）
4. 守るべき体験・設計原則に反していないか
5. 意図的に対象外とした領域に踏み込んでいないか
6. プロジェクト固有の制約に違反していないか
7. 人間の判断・承認が必要な領域ではないか

「PROJECT からは判断できない」が正しい答えになるのは、その案が詳細設計の問題である場合に限る。

### 1.3 責務

PROJECT が持つもの:
- 背景・課題・目的・提供価値と、それらの因果関係
- 対象（利用者・受益者・購入者など）
- 解決の基本方針と、守るべき原則
- プロジェクト全体のスコープと、意図的な非対象
- 事業・運用・法務上の重要な前提と制約
- 重要な仮説と、企画レベルの未決定事項

これ以外は他の文書の責務とする（6章）。

## 2. 基本原則

| # | 原則 | PROJECT が満たす状態 |
|---|---|---|
| P1 | なぜ作るかが先にある | 背景・課題・目的・価値の関係が、機能の説明より先に示されている |
| P2 | 機能と提供価値を区別する | 機能に触れる場合、その機能が誰に何の変化をもたらすかと結びついている |
| P3 | 判断基準になる | 原則・方針が、後続の判断で照合できる具体性を持っている |
| P4 | 非対象は必要なものに絞る | 非対象・責任境界が、判断が分かれうるものに絞られている |
| P5 | 確定度を混同しない | 決定・仮説・提案・未決定が区別されている（3章） |
| P6 | 成立条件は技術的でも残す | プロジェクトの前提となる制約が書かれており、実現方式の詳細は含まれていない |
| P7 | 分量は性質に従う | 分量がプロジェクトの性質に見合っている。短さ・長さそのものは評価の対象にしない |

## 3. 確定度

| 区分 | 意味 | 後続の読者にとっての扱い |
|---|---|---|
| 決定 | 人間が承認した事項 | 前提として判断に使ってよい |
| 仮説 | 採用しているが、検証で覆りうる前提 | 前提として使うが、検証の対象である（C5） |
| 提案 | AI などが示し、まだ承認されていない案 | 前提として使わない |
| 未決定 | 論点として認識しているが、決まっていない | 決定として扱わない |

要件:
- **K1** 確定度の表記方法が文書内で一度示され、文書全体で統一されていること。表記の形式（ラベル、記号、節の分け方など）は問わない。
- **K2** ラベルのない記述は「決定」として読まれる。そのため、人間が承認していない内容（AI の提案や推測を含む）が、ラベルなしで書かれていないこと。
- **K3** 文書全体が企画段階で、大半が未確定である場合は、その状態が冒頭で示されていること。この場合、個別のラベルは特に重要な箇所に限ってよい。
- **K4** 不明な事項が、推測によって確定したかのように書かれていないこと。**未決定事項が存在すること自体は欠陥ではない。**
- **K5** 仮の値（仮の価格など）には、仮であることが併記されていること。
- **K6** 決定として書かれた事項が、入力中の明示的な合意・判断に基づいていること。
  - 後から出た検討や提案が、それより前の決定を上書きした形で書かれていないこと。ただし、変更の合意が確認できる場合を除く。
  - 撤回された案や置き換えられた案が、現行の決定として残っていないこと。
  - 合意したかどうかを判断できない事項（AI の提案に肯定的な反応をしただけ、など）が、決定として書かれていないこと。

## 4. 内容の要件

### 4.1 必須観点（M）

どのプロジェクトでも、PROJECT から読み取れること。決まっていない事項は、未決定として明示されていること。
観点ごとに独立した章である必要はなく、自然な文章に統合されていてよい。

| ID | 観点 | 満たす状態 | 不十分な状態の例 |
|---|---|---|---|
| M1 | 存在意義 | なぜやるのか、やらないと何が困るのかが、冒頭近くで1〜3文程度で分かる | 製品の説明だけで、目的が書かれていない |
| M2 | 背景・課題 | 誰の、どんな問題かが具体的で、既存の手段では解けない理由が分かる | 一般論にとどまる。課題が「〜機能がない」という機能の裏返しになっている |
| M3 | 対象 | 誰が使い、誰が価値を受け取るかが、判断に効く粒度（属性・状況）で特定されている | 「すべての人」。立場を並べただけで違いが分からない |
| M4 | 提供価値 | 課題が解決されると誰に何が変わるかが、M2 の課題と対応している | 機能の列挙になっている |
| M5 | 基本方針 | どのような考え方で課題を解くかが、他のやり方ではなくこれを選ぶ理由とともに分かる | 技術選定の羅列になっている |
| M6 | スコープ | 何を実現し、何を対象外とするかについて、判断が分かれうる境界が引けている | 機能の一覧になっている。非対象が過剰に列挙されている |

M2（課題）→ M5（方針）→ M4（価値）の因果がつながっていること（Q2）。

### 4.2 条件付き観点（C）

適用条件に当たる場合に、PROJECT から読み取れること。**この一覧は章立てではない。**

| ID | 観点 | 適用条件 | 満たす状態（PROJECT の粒度） | 含めないもの |
|---|---|---|---|---|
| C1 | 体験・設計原則 | 体験が価値の中心である。対象者に特性がある（子ども、高齢者、専門家など） | 後続の UI・機能判断に使える「〜する／〜しない」形式の原則がある。例示は1つ程度まで | 画面ごとの挙動、具体的な数値 |
| C2 | 立場の区別 | 利用者・購入者・管理者・出品者など、立場によって求めるものが異なる。両面市場である | 立場ごとの課題と価値、立場間で利害が衝突したときの優先順位が分かる | 権限表、ロールの定義 |
| C3 | 事業・収益モデル | 商用である | 誰から何に対して対価を得るか、採用しない収益方式とその理由が分かる | 価格表、課金アイテムの定義、課金処理 |
| C4 | 差別化 | 競合や代替手段がある | 何で勝つか、何では勝てないと見ているかが分かる | 機能比較の詳細 |
| C5 | 成功指標・検証仮説 | 事業や利用に関する仮説を検証する必要がある | 仮説と、それを確かめる指標（定性的でもよい）、成功と見なさないものが分かる | 計測の実装、ダッシュボード |
| C6 | 法務・規制・責任境界 | 金銭、個人情報、権利、未成年、規制業種、ストア審査などを扱う | 引き受けない責任、守るべき規制上の前提、専門家の確認が必要な点が分かる | 条文解釈の詳細、規約の本文 |
| C7 | AI と人間の分担 | AI の自律作業を制限すべき領域がある | 人間の承認が必要な判断・操作と、その理由が分かる | 作業手順、チェックリスト |
| C8 | 段階的展開 | MVP、複数のフェーズ、段階的なターゲット設定がある | 各段階の狙い、次の段階へ進む条件、今どの段階を優先するかが分かる | フェーズ内の作業計画、日程 |
| C9 | 既存製品・資産との関係 | 刷新、移行、並行運用、資産の流用がある | 既存との関係（置き換え／並存／流用）と、守るもの・捨てるものが分かる | 移行の手順 |
| C10 | 運用・体制上の制約 | 予算、人員、保守負荷が基本設計を左右する | 制約と、それが方針に与える影響が分かる | 具体的な運用設計 |
| C11 | 重要用語 | 一般的な意味と異なる用語や、誤解すると設計を誤る用語がある | プロジェクト固有の用語とその定義がある | すべてのデータ項目の辞書 |

### 4.3 観点の適用

- 適用条件に当たる観点は、記述されているか、未決定として明示されていること。
- 適用条件に当たらない観点の記述や、「該当なし」という章がないこと。
- 一覧にない観点を含めてもよい。ただし、記載判断テスト（6.1）を満たし、既存の観点の言い換えではないこと。例: コンテンツの品質管理方針、データの正確性の担保、提供地域・言語。

## 5. 構成の要件

- **S1** 冒頭で、読者が「何を・誰に・なぜ」をすぐに掴めること。
- **S2** 冒頭に、文書の状態、更新日、確定度の表記方法（K1）が示されていること。
- **S3** 原則・非対象・制約・未決定が本文に埋もれておらず、後続の読者が照合しやすいまとまりになっていること。
- **S4** 構成がそのプロジェクトで比重の大きい観点を反映しており、観点名を章名として並べただけになっていないこと。見出しにプロジェクト固有の言葉（例: 「テストではなく旅にする」）を使ってよい。

## 6. 他ドキュメントとの境界

### 6.1 記載判断テスト

情報の種類だけで機械的に分類しない。PROJECT に含まれる記述は、次の3つを満たすこと。

1. **判断への影響**: それがないと、後続の採用・不採用・優先順位の判断を誤る。
2. **範囲**: プロジェクト全体（または複数の機能）に効く。
3. **持続性**: 実装方式や進捗が変わっても有効である。

ただし、プロジェクトの**成立条件**に当たる内容は、範囲や持続性を満たさなくても、「何を守るか・なぜか」の形で含まれていること。その場合も「どう実現するか」は含まれていないこと。

| 情報 | PROJECT にあるべき形 | 委ねる先 |
|---|---|---|
| サーバレス構成を採用する | 「常時稼働のサーバーを持たない。低コストかつ少人数での運用が成立条件であるため」 | Lambda / S3 の構成、デプロイ方式 → ARCHITECTURE |
| 誤答時のヒント表示の仕様 | 「まちがえても責めない」という原則 | ヒントを出す回数や表示内容 → FUNC / SPEC |
| ランキングの算定ルール | 「人気指標は、水増しされにくいものにする」 | 算定式、除外条件 → SPEC |
| 個人データを収集しない | そのまま制約として | 実装上の担保方法 → ARCHITECTURE / SPEC |
| 試作版の実装状況、データの作成状況 | 含まない | STATUS |
| アプリの識別子、対応OSのバージョン | 含まない（方針である場合を除く） | SPEC / README |

### 6.2 他の文書の責務

| 文書 | 責務 |
|---|---|
| ARCHITECTURE | システム全体の構成、コンポーネントの責務、技術的な依存関係、データの流れ、外部連携の構成、インフラ構成 |
| FUNC | 個別機能の目的と役割、機能単位の振る舞い、利用者と機能の関係、機能ごとの提供範囲 |
| SPEC | 画面操作、API、データ構造、状態遷移、入力チェック、例外処理、実装・検証に必要な詳細 |
| STATUS | 実装の進捗、直近の作業、未完了のタスク、既知の不具合、作業再開に必要な状態 |
| AGENTS | AI の作業手順・規約・コマンド（AI に任せない理由は C7 として PROJECT の責務） |

### 6.3 未決定事項の PROJECT / STATUS 分担

判定の問いは「決まったら、PROJECT の記述が変わるか」である。

- 企画レベルの未決定事項（決まると PROJECT の記述が変わるもの）が、内容と影響範囲が分かる形で PROJECT に含まれていること。
- 企画レベルの未決定事項が、STATUS にだけ置かれている状態でないこと。
- 実務上の未完了事項（決まっても PROJECT の記述が変わらないもの）が、PROJECT に含まれていないこと。
- 同じ論点の中身が、PROJECT と STATUS の両方に複製されていないこと。STATUS からは PROJECT を参照する。

### 6.4 肥大化と重複

- 同じ事実が、文書内や他の文書と重複していないこと。他の文書にある内容は、参照で済ませていること。
- **原則はあり、規則はない**こと。原則に添える例示は1つまで。
- **方針はあり、方式はない**こと。
- 非対象は、誤って作りそうなもの、議論の末に却下したもの、外部から期待されそうなものに限られていること。理由は、判断が分かれたものに付いていること。
- 経緯は、判断の理由が後で必要になるものに限られ、要点だけになっていること。
- 日付付きの状態、数量、進捗、担当者が含まれていないこと。
- 具体的な値（価格、件数、ID、バージョン）は、それ自体が方針である場合に限って含まれていること。例: 「広告を入れない」は方針。仮の価格は確定度付きで含めてよい。アプリの識別子は含めない。
- 存在しない文書への参照がないこと。

## 7. 品質の判定

### 7.1 品質観点（Q）

| ID | 観点 | 満たす状態 | 関連 |
|---|---|---|---|
| Q1 | 目的の明確性 | 冒頭近くで、なぜ作るのかが分かる | M1, S1 |
| Q2 | 因果関係 | 課題・方針・価値が対応している。対応する課題のない価値や、対応する価値のない課題がない | M2, M4, M5 |
| Q3 | 対象の明確性 | 誰に何を提供するかが分かる。立場による違いが価値に反映されている | M3, C2 |
| Q4 | 一貫性 | 目的・スコープ・方針・制約・原則の間に矛盾がない | 全体 |
| Q5 | スコープの明確性 | 変更案の採用・不採用を判断できる境界がある | M6 |
| Q6 | 確定度の識別 | 決定・仮説・提案・未決定が区別でき、未承認の内容が決定として書かれていない | 3章 |
| Q7 | 責務境界 | 記載判断テストに反する記述（詳細仕様、技術の詳細、進捗）や重複が、判断を妨げるほど混ざっていない | 6章 |
| Q8 | 判断への有用性 | 判断テスト（1.2）に答えられる | 1章 |
| Q9 | 入力との整合 | 入力資料の重要事項が反映されている（または他の文書の責務として除かれている）。入力にない事項が決定として書かれていない。入力の意図が歪められていない | — |

### 7.2 重大度と合否

**要修正**（そのままでは後続の判断を誤らせる）:
- 目的・対象・スコープの間の重大な矛盾（Q4）
- 提案・推測・未決定が、決定として書かれている（Q6）
- 撤回・置換された案や、合意が確認できない事項が、決定として書かれている（K6）
- 入力にない重要事項の捏造、または入力の歪曲（Q9）
- M 観点が欠けていて、判断テストに答えられない（Q8）
- 入力で明示された重要な制約や非対象が欠けている（Q9）

**推奨**（品質を上げるが、直ちに判断を誤らせるものではない）:
- 境界外の記述の混在（Q7）。ただし、進捗や状態の情報は古くなると判断を誤らせるため、優先度を高くする
- 因果のつながりの弱さ
- 適用条件に当たる C 観点が、記述も未決定としての明示もない
- 非対象の過剰な列挙、重複

**参考**: 表現や読みやすさ

**合否**: 要修正が0件であれば合格とする。点数化はしない。目的に関わる重大な矛盾が1件でもあれば、他の観点がすべて満たされていても不合格とする。

### 7.3 欠陥とみなさないもの

- 文書が短いこと
- 適用条件に当たらない C 観点が書かれていないこと
- 未決定の事項が多いこと（決定と区別されている限り）
- 章立てが他のプロジェクトと異なること
- 確定度のラベルがないこと（ラベルのない記述がすべて、実際に決定済みである場合）

## 8. 更新が必要な状態

判定の問いは「この変化によって、判断テスト（1.2）の答えが変わるか」である。

次の変化が反映されていない PROJECT は、古くなっている。
- 対象ユーザー、解決する課題、提供価値の変更
- 事業・収益モデルの重要な変更
- 基本方針、守るべき原則の変更
- スコープの大きな変更
- プロジェクト成立の前提条件や制約の変更
- 仮説の検証結果（決定への昇格、または破棄）
- 企画レベルの未決定事項の解決
- C 観点の適用条件に当たるかどうかの変化（例: 商用化した、個人情報を扱い始めた、AI に任せる範囲が変わった）

次の変化だけでは、PROJECT の更新を要しない。
- 機能・画面・API の追加や変更
- 技術方式の変更（成立条件に触れない場合）
- 進捗、詳細仕様の変更

更新後の PROJECT は、次を満たすこと。
- 置き換えられた古い記述が残っていないこと。
- 重要な判断を変えた場合、その理由が残っていること（決定記録があればそちらに、なければ PROJECT に短く）。
- 既存の決定が、人間の承認なしに変更されていないこと。
