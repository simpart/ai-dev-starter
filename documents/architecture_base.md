# ARCHITECTURE 共通基準

> 状態: 草案 v0.1（2026-11-04）
> 本書は、生成先プロジェクトの `ARCHITECTURE.md` が**満たすべき状態**を定義する。生成・レビュー・更新で同じ基準を使う。
> AI の作業順序、利用ツール、レビュー手順は定義しない。また、本書は章立てのテンプレートではない。

---

## 0. 本書の適用と基本動作

ユーザーから本書を参照して `ARCHITECTURE.md` を生成・レビュー・更新するよう依頼された場合、依頼された作業の範囲に本書の該当基準を適用する。

- 会話、既存の `PROJECT.md`、その他の提供資料における**最終的な合意**を反映し、過去の案と混同しない（K6）。
- 全体構成図を含め、システムの構成要素・責務・主要な連携・境界を把握できる成果物にする。
- 他文書の責務に属する個別機能や実装の詳細を混在させない。ただし構成上の判断を成立させる条件は残す（6章）。
- 7.2 の「要修正」が0件となる品質を目指す。根拠不足のため解消できない事項は推測で埋めず、未決定として区別する。
- 本文に含めなかった重要な決定・検討事項、また設計の成立を左右する未決定事項は、必要に応じて成果物とは別に示す。

ユーザーの依頼がレビューのみであれば、生成・更新まで行うことを意味しない。個別指示と本書の基準に相違がある場合は、無言で基準を無効化せず、相違を明らかにする。

## 1. ARCHITECTURE の目的と責務

### 1.1 目的

ARCHITECTURE は、システムが**どの構成要素から成り、各要素が何を担当し、どのように連携して全体として成立するか**を示す文書である。

主な読者は、設計・実装・変更を行う AI エージェントおよび人間である。機能一覧やコードの説明書ではなく、**変更箇所・変更影響・責任の所在を判断するための構造上の正本**とする。

### 1.2 判断テスト

新機能、変更、障害対応を検討する際、ARCHITECTURE から以下を判断できること。

1. その責務を担う構成要素はどこか。既存の責務に属するか、新たな境界が必要か。
2. 利用者・クライアント・内部要素・外部依存はどのようにつながるか。
3. 重要なデータは誰が保持・更新し、どこが正本となるか。
4. どこで認証・認可・検証・取引確定などを担保するか（該当する場合）。
5. 変更が影響する構成要素、連携、データ、信頼境界はどこか。
6. 採用済みの構成方針・実行環境・制約と矛盾しないか。
7. 未決定・仮説の構成判断が何で、どこに影響するか。

API のフィールド、画面遷移、アルゴリズム内部の分岐など、下位設計に属する問いまで答える必要はない。

### 1.3 責務

ARCHITECTURE が持つもの：

- システム全体を俯瞰できる**構成図**と、その説明
- 利用者・クライアント・主要構成要素・外部依存の関係
- 各構成要素の責務、所有する状態・情報、要素間の境界
- 主要なデータ・制御の流れ、重要な処理の確定主体
- 構成を左右する技術選択・設計原則・成立条件
- アーキテクチャ上の重要な未決定事項と、採用した判断の根拠

個別機能の挙動、画面操作、API・データ形式、実装進捗は原則として他文書の責務とする（6章）。

## 2. 基本原則

| ID | 原則 | ARCHITECTURE が満たす状態 |
|---|---|---|
| P1 | 全体から部分を把握できる | 全体構成図があり、説明と対応している |
| P2 | 要素の責務が識別できる | 機能の羅列でなく、何をどこで担うかが分かる |
| P3 | 境界と依存が明確 | システム内外、要素間、信頼・データの境界が追える |
| P4 | データの正本が曖昧でない | 重要な状態・取引の正本、更新主体、整合性上の責務が分かる |
| P5 | 論理と物理を混同しない | 役割・責務と、配置先・製品・技術スタックを区別できる |
| P6 | 構成判断の理由がある | 重要な選択の理由と制約が分かり、技術名の列挙に終わらない |
| P7 | 決定の確定度を守る | 決定・仮説・提案・未決定を混同しない（3章） |
| P8 | 粒度を守る | 構造・責務に必要な具体性は残し、詳細仕様や進捗は蓄積しない |
| P9 | 文書の分量は構造の複雑さに従う | 固定の行数、図の数、章数で品質を判断しない |

## 3. 確定度

| 区分 | 意味 | 後続の読者の扱い |
|---|---|---|
| 決定 | 人間が承認した構成判断 | 設計上の前提として扱える |
| 仮説 | 検証を前提に採用している構成 | 暫定前提として使えるが検証対象 |
| 提案 | 未承認の構成案 | 決定事項として実装しない |
| 未決定 | 判断を要するが結論がない事項 | 決定として扱わない |

- **K1** 確定度の表記方法が一度示され、全文で統一されていること。形式は自由。
- **K2** ラベルのない構成・方針は決定として読まれる。未承認の提案・推測が無標記の決定として書かれていないこと。
- **K3** 構想・試作段階で大半が未確定の場合、冒頭でその状態が分かること。重要箇所は個別にも識別できること。
- **K4** 未決定事項の存在自体を欠陥とせず、不明な構成を推測で確定しないこと。
- **K5** 暫定の技術・数値・構成は暫定であると分かること。
- **K6** 決定事項は、提供された資料・会話における明示的な合意・判断に基づくこと。
  - 後からの検討案で、以前の決定を無断で上書きしないこと。
  - 撤回・置換された案を現行構成として残さないこと。
  - AI に選定を委ねた場合は、委任範囲と選定結果への合意の有無を区別すること。

## 4. 内容の要件

### 4.1 必須観点（M）

すべての ARCHITECTURE から読み取れること。独立した章である必要はない。設計が未確定なら、そのことが分かること。ただし **M1 の図そのものは必須**であり、未決定の構成は未決定と表示した図を用いる。

| ID | 観点 | 満たす状態 | 不十分な状態の例 |
|---|---|---|---|
| M1 | 全体構成図 | システムの主な利用者・入出力、主要要素、データ保持先、外部との関係を、対象に合った抽象度の図で俯瞰できる | 構成図がない。詳細なファイル一覧しかない |
| M2 | 主要構成要素と責務 | 図に登場する主要要素が何を担い、どこまで責任を持つか分かる | 「API」「DB」などの名前だけで責務が分からない |
| M3 | 連携・主要な流れ | 重要な情報・処理が要素間をどう移動し、どこで処理・確定するか追える | 矢印の意味が不明。重要な処理経路が欠落 |
| M4 | データの管理責任 | 重要なデータ・状態の保持主体、正本、更新主体が識別できる | 同じデータが複数箇所に存在し、正本が不明 |
| M5 | システム・責任境界 | 内部・外部、クライアント・処理側、信頼境界など主要な境界が分かる | 利用者端末とサーバーの責任が混同される |
| M6 | 構成上の基本方針・制約 | 主要な構成選択の理由と守るべき条件が示される | 採用技術名だけで、選定理由・成立条件が不明 |

### 4.2 条件付き観点（C）

該当する場合に、構造・責務・境界の粒度で含めること。**以下は章立てではない。**

| ID | 観点 | 適用条件 | ARCHITECTURE に必要な情報 | 委ねる詳細 |
|---|---|---|---|---|
| C1 | 技術スタックと採用理由 | 技術選定が要素・責務・依存関係を左右する | 主要領域ごとの採用技術と理由、代替不能な制約 | ライブラリの細かな設定、コマンド |
| C2 | 実行・配置構成 | クラウド、端末、複数環境、BYOCなどがある | 配置先と管理主体、論理要素との対応、環境間の境界 | IaCの定義、デプロイ手順 |
| C3 | 認証・認可・信頼境界 | 利用者認証、権限分離、外部入力がある | 認証・認可・検証の責務と適用境界 | ロール別操作一覧、トークン仕様 |
| C4 | 整合性・取引の確定 | 決済、残高、競合更新、重要な状態変更がある | 正本、取引の確定主体、整合性・再送耐性の責任 | 状態遷移表、例外分岐、SQL |
| C5 | 非同期・イベント連携 | キュー、イベント、バッチ、ジョブがある | 起点・処理主体・結果の所在、配送失敗や重複の責任 | イベントペイロード、再試行回数 |
| C6 | 性能・可用性・拡張性 | これらが構成選択を左右する | 構造上のボトルネック・分散方針・障害時の責任 | ベンチマーク結果全文、チューニング値 |
| C7 | 外部サービス・SDK依存 | 外部API、OS、ストア、マネージドサービスを使う | 依存先、境界、代替・障害時の構造的影響 | SDKの呼び出しコード、エラー文言 |
| C8 | 複数プラットフォーム | Web・iOS・Androidなどを共通化する | 共通部分と環境固有部分の責務分離 | 個々のプラグインAPI |
| C9 | 既存構成との並存・移行 | 試作から本番、旧新並存、段階移行がある | 目標構成・現行構成の区別、依存・移行境界 | 移行作業の工程や進捗 |
| C10 | 監視・運用・障害対応 | 運用方式が構成を決める | ログ・メトリクス・監視の責任主体、障害の隔離・復旧境界 | アラート閾値、当番手順 |
| C11 | 主要な情報モデル | ドメイン間の関係が構成の理解に不可欠 | 主要データの概念・所有者・関係 | 全フィールド、型、バリデーション |
| C12 | 拡張・差し替え境界 | プラグイン、アダプタ、複数バックエンド等を想定 | 交換できる単位と依存方向 | メソッドシグネチャ、個別実装 |
| C13 | 分離・マルチテナント | テナント、組織、顧客環境の分離が必要 | 分離の単位、責任主体、データ境界 | テーブル定義、詳細ポリシー |

### 4.3 適用の考え方

- 適用する C 観点は、ARCHITECTURE に記載されるか、設計上重要な未決定として識別できること。
- 該当しない観点を「該当なし」の章で埋めないこと。
- 上記にない観点も、1.2 の判断に必要なら加えてよい。既存観点の言い換えや、機能仕様の持ち込みは避けること。
- 設計が小規模で構成要素が少なくても、架空の層やコンポーネントを増やして体裁を合わせないこと。

## 5. 構成図と文書構成の要件

### 5.1 全体構成図

- **D1** 全体を示す図が少なくとも1つあること。Mermaid、ASCII、その他の形式を問わない。単一プロセスのツールでも、入力・処理・状態・外部依存の関係を示す。
- **D2** システム内外、実行場所、管理主体など、構造判断に重要な境界が区別できること。境界がないものを無理に描かない。
- **D3** 主な接続・データまたは制御の方向が読み取れること。矢印や線の意味が紛らわしい場合は説明があること。
- **D4** 図にある主要要素と本文の責務説明が対応し、名称・依存関係が矛盾しないこと。
- **D5** 現行構成、目標構成、提案・未決定の構成を、同じ図の中で確定済みとして混同しないこと。必要なら図を分ける。
- **D6** 図の抽象度を保つこと。画面単位の操作、全API、全テーブル、全ソースファイルを全体構成図に詰め込まないこと。

論理構成図は原則必須とする。物理・デプロイ構成図、主要フローのシーケンス図、データ概念図は、それぞれ構成上の判断に必要な場合に加える。図の数を固定しない。

### 5.2 文章の構成

- **S1** 冒頭で対象システムと文書が定義する範囲、構成上の主要方針を把握できること。
- **S2** 文書の状態・更新日・確定度の扱いが分かること。
- **S3** 全体構成図、主要要素の責務、重要な境界・連携が見つけやすいこと。
- **S4** 対象システムに適した構成であり、基準の M/C 項目を機械的に見出しへ写さないこと。

## 6. 他ドキュメントとの境界

### 6.1 記載判断テスト

ARCHITECTURE に載せる主な判断基準は、その情報が**システム全体の構造、要素の責務・所有権、依存関係、信頼・データの境界、あるいは構造上の成立条件**を定めるかどうかである。

- 全体または複数の構成要素の判断を変える記述は、ARCHITECTURE に残す。
- 単一機能の内容でも、処理の確定主体、データの正本、信頼境界を決めるものは残せる。
- 特定の構成要素の内部実装や個別の画面・機能の振る舞いしか定めない記述は、原則として FUNC / SPEC に委ねる。
- ファイル構成は、明確なモジュール境界・依存方向を説明する場合に限り必要な粒度で扱う。網羅的なファイルツリーを必須にしない。
- 図や説明に技術製品名を用いてよい。ただし、技術名を羅列するだけで設計意図を省略しない。

| 情報 | ARCHITECTURE に残す内容 | 委ねる先 |
|---|---|---|
| サーバーを持たず端末と静的配信で成立させる | クライアント・配信元・保存の責務と構成 | データ取得の例外表示・タイムアウト → FUNC / SPEC |
| Webとネイティブの機能を分離する | 共通ロジックとプラットフォーム固有アダプタの境界 | プラグインAPI、メソッド定義 → SPEC |
| Ticket残高をクラウド上の台帳で確定する | 正本・確定主体・二重処理防止の責任 | 使用操作、状態遷移の全条件 → FUNC / SPEC |
| 検索処理と管理処理を分ける | data-plane / control-plane の役割と配置 | APIパラメータ、認証処理の詳細 → SPEC |
| 路線やカタログのデータを保持する | 配信先、保存先、更新・キャッシュの責任 | JSONフィールド、入力検証ルール → SPEC |
| 負荷試験で特定の性能値が出た | 構成選択に効く検証済み制約・課題だけ | 試験結果全文・測定条件・計画 → 検証記録 / STATUS |
| 開発用コードやディレクトリを配置する | 構成要素間のモジュール境界が必要ならその範囲 | ファイル一覧、コマンド → 開発者向け資料 |

### 6.2 文書ごとの責務

| 文書 | 責務 |
|---|---|
| PROJECT | 何のために作るか、誰にどんな価値を提供するか、企画上の原則・非対象・成立条件 |
| ARCHITECTURE | システム全体の構成、主要要素の責務・依存、データ・信頼境界、構成を左右する技術方針 |
| FUNC / FUNCTIONS | 個別機能の目的、役割、利用者との関係、機能ごとの振る舞い・提供範囲 |
| SPEC | 画面操作、API、スキーマ、状態遷移、バリデーション、計算、実装・検証に必要な詳細 |
| STATUS | 現在の実装状態、作業の進捗、短期の課題、検証待ち、既知の不具合 |
| AGENTS / CLAUDE | エージェントの作業ルール、利用ツール、実行手順 |
| DECISIONS / ADR・検証記録（存在する場合） | 設計判断の詳しい経緯、比較した代替案、試験結果と証拠 |

### 6.3 未決定と現行・目標の分担

- 「決まれば構成図、要素の責務、依存、信頼・データ境界が変わるか」を、ARCHITECTURE に残す未決定事項の判断基準とする。
- 実装が終わっていないことと、構成が未決定であることを混同しない。実装進捗は STATUS に置く。
- プロトタイプ構成と採用予定の目標構成は区別する。実装済みという事実だけで目標構成を決めない。
- 決定の理由は、構成理解に必要な要点を残す。詳細な議論経緯は決定記録へ委ねる。

### 6.4 肥大化と重複

- 他文書にある詳細は参照で済ませる。ただし、ARCHITECTURE の責務を理解するための要点まで省略しない。
- 全メソッド、全画面、全データフィールド、設定値、手順・作業ログを収録しない。
- 固定の図法、クラウド製品、レイヤー数、ディレクトリ構成を強制しない。
- 存在しない文書を参照しない。

## 7. 品質の判定

### 7.1 品質観点（Q）

| ID | 観点 | 満たす状態 | 関連 |
|---|---|---|---|
| Q1 | 全体可視性 | 全体構成図から対象・主要要素・外部関係を把握できる | M1, D1–D6 |
| Q2 | 責務の明確性 | 主要要素の役割・所有する情報が分かり、不自然な空白・重複がない | M2, M4 |
| Q3 | 連携の追跡可能性 | 重要な情報・制御の流れと、処理の確定主体を追える | M3 |
| Q4 | 境界の整合性 | 信頼境界、データ正本、実行場所、依存関係が矛盾しない | M4, M5 |
| Q5 | 設計判断への有用性 | 変更場所・影響範囲・構成制約を判断できる | 1.2, M6 |
| Q6 | 確定度 | 未承認の提案・推測と合意済み構成が区別される | 3章 |
| Q7 | 文書の責務境界 | FUNC / SPEC / STATUS と重複せず、構造上の必要事項は落ちていない | 6章 |
| Q8 | 図文一致・内部一貫性 | 図と本文・各構成要素の説明が矛盾しない | 5章 |
| Q9 | 入力・PROJECTとの整合 | 上位の目的・制約・合意を踏まえ、入力にない事項を決定として追加しない | PROJECT, K6 |

### 7.2 重大度と合否

**要修正**（残すと構成判断や実装担当の判断を誤らせる）：

- 全体構成図がない、または図から主要構成・境界を把握できない（Q1）。
- 主要要素の責務・重要なデータの正本・処理の確定主体が曖昧で、設計判断を誤らせる（Q2–Q4）。
- 図と本文、または配置・依存・信頼境界に重大な矛盾がある（Q4, Q8）。
- 未承認の構成案、撤回済みの選択を決定として記載している（Q6, K6）。
- PROJECT の成立条件・明示された制約に反する、または重要な入力を歪曲・欠落させている（Q9）。
- 必須観点の欠落で、1.2 の構成判断テストに答えられない（Q5）。

**推奨**（改善余地があるが、直ちに重大な判断ミスを生むわけではない）：

- 図の可読性・名前の統一が弱い。
- 条件付き観点が該当するのに説明または未決定としての明示が不十分。
- 詳細仕様や現時点の試験結果・進捗が混在する。
- 決定理由が薄い、または同一情報が重複している。

**参考**：表現、体裁、読みやすさ。

**合否**：要修正が0件なら合格。点数化しない。未決定事項が残っていても、その状態と影響が識別できれば、それだけで不合格とはしない。

### 7.3 欠陥とみなさないもの

- プロジェクト規模に応じて文書が短いこと。
- 物理構成図、詳細シーケンス図、ER図、ファイルツリーがないこと（必要性がない場合）。
- 非適用の C 観点を省いたこと。
- 技術製品名が未決定であること（構造上の役割・責務が説明できている場合）。
- 図や章の形式が他プロジェクトと違うこと。

## 8. 更新が必要な状態

判断の問いは、**「この変更によって、1.2 の構成判断テストの答えが変わるか」**である。

次の変化が未反映なら、ARCHITECTURE は古くなっている。

- 主要構成要素の追加・廃止・統合・責務の移動。
- 構成要素間の接続、データ・制御の流れの変更。
- データの正本、保存場所、更新主体、整合性の責任の変更。
- 認証・認可、信頼境界、テナント境界の変更。
- 実行環境、配置先、外部依存の重要な変更。
- 全体構成・構成原則・成立条件に影響する技術選択の変更。
- 現行・目標構成の位置づけ、重要な構成仮説・未決定事項の解決。

次の変更だけでは、通常は ARCHITECTURE の更新を要しない。

- 既存要素の内部処理の変更、API項目や画面の微修正。
- 構造・責務に影響しない設定値やライブラリの更新。
- 実装進捗や検証タスク、テスト結果の更新。

更新後は、**図と本文が揃い、旧構成が現行として残らず、承認済みの構成判断が無断で変更されていない**こと。
