# STATUS 共通基準

> 状態: 草案 v0.1（2026-11-05）  
> 本書は、開発の現在状態と作業履歴を管理する `status/` 一式が**満たすべき状態**を定義する。新規生成・レビュー・更新で同じ基準を使う。  
> 特定のAI、開発手法、タスク実行器、ワークフローには依存しない。固定の章立てや逐次的な作業手順を規定する文書ではない。

---

## 0. 本書の適用と基本動作

本書を参照してSTATUSの生成・更新・評価を依頼された場合、依頼の対象に応じて本書を適用する。基本となる成果物は、現在状態の `status/CURRENT.md` と、必要に応じた `status/history/*.md` である。

- `CURRENT.md` が、今どこまで進み、次に何をするかを、過去の経緯を読まずに判断できる状態であること。
- 履歴は作業・変更のまとまりごとに分離し、経緯・検証結果・判断の根拠を後からたどれること。
- 実施・確認・承認していない事柄を、完了や決定として書かないこと。
- 更新後に、現状・タスク・未解決事項・履歴の間に食い違いがないこと。
- 本書の品質判定（7章）で「要修正」が0件であること。未決定や未完了の項目が存在すること自体は欠陥としない。

STATUSの新規作成を求められた場合も、根拠のない進捗や日付を補完しない。情報が不足する場合は、確認できる現状を示し、未確認事項として区別する。

## 1. 目的・責務・正本

### 1.1 目的

STATUSは、**AIエージェントや人間が、開発の現在位置、未完了の作業、妨げとなっている問題、次の着手先を把握し、中断後でも作業を再開できるようにする運用情報の正本**である。

STATUSはプロジェクトの目的・システム構造・機能仕様の正本ではない。それらへの参照と、現在の実施状態を管理する。

### 1.2 責務の分離

| 所在 | 正本として持つ情報 | 持たない情報 |
|---|---|---|
| `status/CURRENT.md` | 現在の進捗、現時点で有効なタスク、優先順位、担当、完了条件、判断待ち・阻害要因、再開に必要な短い文脈 | 終了済み作業の詳細な経緯、古いTODO、日記式の追記、個別機能の仕様全文 |
| `status/history/*.md` | 実施済みの作業・変更の経緯、結果、検証の根拠、当時の制約、引き継ぎ事項 | 現在のタスク一覧の独立した複製、最新状態の第二の正本 |
| PROJECT / ARCHITECTURE / FUNC / SPEC 等 | 目的・方針、構造・責務、機能・詳細仕様の正本 | 現在の作業進捗や作業ログ |
| Git / CI / 外部タスク管理・各種ログ | コード変更、実行証跡、外部システム上の記録 | STATUSが担う現在状態の説明そのもの（参照は可能） |

履歴は原則として追記・新規作成で蓄積する。ただし誤記修正、情報保護、参照切れの修復など、記録を正しく保つための訂正は許容する。訂正によって判断の経緯を不当に書き換えない。

### 1.3 再開判断テスト

`CURRENT.md` を最初に読んだ人・AIが、必要に応じて参照先を開けば、次の問いに答えられること。

1. 現在の到達点と、直近の重要な変化は何か。
2. 次に着手すべき作業は何か。優先順位や依存関係は何か。
3. 各作業は誰の担当で、何をもって完了とするか。
4. どの作業が進行中・停止中・未着手・完了なのか。
5. 何が未確認・判断待ち・阻害要因で、誰または何が解消できるか。
6. 現状や過去の判断を検証するには、どの資料・履歴・成果物を参照すればよいか。

## 2. 基本原則

| ID | 原則 | 満たす状態 |
|---|---|---|
| P1 | 現状を優先する | CURRENTの冒頭から、最新の到達点と次の着手先が分かる |
| P2 | 正本を一つにする | 現状はCURRENT、作業経緯はhistory、仕様や設計の内容は各正本に置く |
| P3 | 完了を検証可能にする | タスクには完了条件があり、完了時には確認できた結果・根拠が残る |
| P4 | 実績と予定を混同しない | 実施済み・作業中・計画・提案・判断待ちが区別できる |
| P5 | 再開に十分、履歴に過剰でない | CURRENTは独立して読める一方、詳細経緯は参照先に委ねる |
| P6 | 変更の連鎖を失わない | 終了した作業の残課題や依存関係が、必要な次のタスク・未解決事項に引き継がれる |
| P7 | 実装・検証を報告どおりとみなさない | 「作成した」「テストした」「確認した」を区別し、確認方法と未確認範囲を偽らない |
| P8 | 運用規模に合わせる | タスク粒度・履歴分割・記述量は規模に比例させ、細かすぎる事務作業を増やさない |

## 3. ファイル配置と識別

### 3.1 基本構成

```text
status/
├── CURRENT.md
└── history/
    ├── <識別子>-<概要>.md
    └── ...
```

- 履歴は**タスクまたは意味のある変更のまとまり**を単位とする。日付だけを理由に分割しない。
- 1つの作業が複数日にまたがっても、意味のある一連の変更なら1つの履歴でよい。
- 小さく密接に関係する複数タスクは、追跡可能性が保てるなら1つの履歴にまとめてもよい。
- 長期・独立した作業を1つの履歴に詰め込まない。複数履歴に分ける場合は、関連するタスクIDや相互参照を残す。
- `history/` 内のファイルは、他の履歴と区別でき、後から探せる名前にする。タスクID・作業名を基本とし、日付は必要なら付す。命名規則をプロジェクト全体で統一する。
- `STATUS.md` というルート直下の別正本は作らない。互換性のための入口が必要な場合は、`status/CURRENT.md` へのリンク・短い案内のみとする。

### 3.2 識別と参照

- 管理するタスクには、プロジェクト内で一意かつ安定したIDを付ける。例: `P2-06`、`TASK-014`。表記形式やフェーズ記号は固定しない。
- IDはタスクの内容が明確に変わらない限り再利用しない。廃止・分割・統合した場合は、追跡可能な参照を残す。
- CURRENTで参照する履歴・仕様・成果物は、存在するファイルパスや識別子を用いる。存在しないリンクを完成済みとして示さない。
- 履歴側は対象タスクIDと成果物・検証根拠を参照できること。CURRENTを一字一句複製しない。

## 4. CURRENT.mdの内容要件

必須なのは情報の役割であり、章立てや表の形式ではない。

### 4.1 必須観点（M）

| ID | 観点 | 満たす状態 |
|---|---|---|
| M1 | 更新時点・現在位置 | 最終確認・更新時点、現時点の開発段階、実際の到達点が把握できる。更新日だけで最新の実態を保証したように書かない |
| M2 | 次の着手先 | 優先すべき直近の作業が少数に絞られ、なぜ次かが必要な範囲で分かる。未解決の依存がある場合は示す |
| M3 | 有効タスク | 現在進行中・未着手・保留中のタスクを、識別子、内容、状態、担当、完了条件とともに追跡できる |
| M4 | 未解決事項 | 判断待ち、調査、ブロッカー、重要なリスクのうち、現在の作業判断に影響するものが分かる。解決済み事項を未解決として残さない |
| M5 | 検証可能な進捗 | 「実装済み」「確認済み」「リリース済み」などの状態が、確認範囲・結果・参照先と矛盾しない |
| M6 | 再開に必要な参照 | 関連するPROJECT・ARCHITECTURE・FUNC・SPEC・履歴・成果物の所在が、必要な範囲で分かる |

### 4.2 条件付き観点（C）

| ID | 観点 | 適用条件 | 満たす状態 |
|---|---|---|---|
| C1 | フェーズ・マイルストーン | 複数段階の計画で進める | 現在位置と段階ごとの到達状態が矛盾しない。完了条件と実績が混同されない |
| C2 | 人間とAIの分担 | 人間の操作・確認・承認を要する | 担当または次の行為者（人／AI／共同）が分かり、AIが代行できない行為が誤って完了扱いされない |
| C3 | タスクの依存関係 | 着手順や前提条件が重要 | 先行タスク、外部待ち、ブロック理由が辿れる |
| C4 | 複数の並行作業 | 複数の開発者・エージェントが並行する | 各作業の責任範囲、状態、競合の可能性が分かる |
| C5 | リリース・運用状態 | 公開、審査、移行、運用などが発生する | 公開済み・申請中・確認待ち等を区別し、次に必要な外部行為が分かる |
| C6 | 期限・外部待ち | 期限、審査、回答、承認などの依存がある | 期限・待機先・確認が必要な条件が分かる。期限や完了見込みを推測で書かない |
| C7 | 中断時の作業引き継ぎ | 作業途中で中断し、再開時に一時情報が不可欠 | 対象ブランチ・作業箇所・試したこと・未検証事項等、再開に不可欠な情報だけがある |
| C8 | 対象外・先送り | あえて今回扱わない項目が今後の誤着手につながる | 対象外・保留の理由と再検討の条件が分かる。PROJECTで定義したスコープを複製しない |

### 4.3 タスクの最小情報

有効タスクには、少なくとも以下の意味が読み取れること。

- **識別子**：他の記録と紐付けられる安定したID。
- **達成したい状態**：抽象的な「対応する」ではなく、どの状態へ変えるのか。
- **状態**：少なくとも未着手・進行中・待機/阻害中・完了・中止/対象外を識別できる。語彙の形式は固定しない。
- **担当・次の行為者**：誰が着手・確認・承認するのか。必要ない場合の形だけの担当欄は要求しない。
- **完了条件**：実行者以外でも、結果が満たされたか判断できる基準。実施方法の詳細ではなく到達条件を書く。
- **必要時の参照・依存**：仕様・変更対象・先行作業・履歴へのリンク。

未着手の作業を過度に細分化して大量登録する必要はない。遠い将来の詳細計画より、今後の作業判断に必要な粒度を優先する。

### 4.4 冒頭サマリーと一覧の整合

- 冒頭の「次にやること」は、後続の有効タスクやブロッカーと一致すること。
- 直近の重要事項を短く示し、完了済み作業の長い経緯を本文冒頭に積み上げないこと。
- 「次にやること」の件数は原則少数にする。例として3件程度は有用だが、固定の上限は設けない。
- フェーズ一覧・タスク一覧・ブロッカー一覧・冒頭サマリーで、同じ作業の状態に矛盾がないこと。

## 5. history/*.mdの内容要件

### 5.1 履歴を作る単位

履歴は**後から参照する価値のある一連の作業・変更**を単位とする。1つのチャット応答、ツール実行、日付ごとに必ず作ることは要求しない。

- タスク完了、重要な方針変更に伴う作業、複数ファイルにまたがる変更、重要な障害対応、失敗・未達に終わった検証などは履歴に残す価値が高い。
- 軽微な修正は、関係する既存タスクの履歴にまとめるか、Gitやテスト記録への参照で足りる場合がある。
- 完了していない作業でも、中断・引き継ぎや判断の根拠として必要なら履歴を残してよい。
- 履歴を作ったことだけで、タスクが完了したとみなさない。

### 5.2 必須観点（H）

| ID | 観点 | 満たす状態 |
|---|---|---|
| H1 | 対象・識別 | どのタスク/変更を扱った記録か、識別子・題名・実施時期から分かる |
| H2 | 目的と実施内容 | 何を達成しようとし、実際に何を変更・調査・試験したかが区別される |
| H3 | 結果 | 完了・一部完了・未達・中止など、作業結果と残った範囲が分かる |
| H4 | 検証・根拠 | 実施した確認方法、確認できた範囲、確認していない範囲、根拠への参照がある。検証がない場合もその旨が分かる |
| H5 | 影響と引き継ぎ | 変更した主要成果物、後続へ影響する問題・決定・未完了事項が追跡できる。なければ無理に作らない |

長い実行ログやコード差分をそのまま複製する必要はない。重要な結果を要約し、コミット、テスト結果、関連文書へリンクする。

### 5.3 履歴とCURRENTの関係

- 完了した作業の詳細は履歴に置く。CURRENTには最新の到達点と、その後の判断に必要な短い結果だけを残す。
- 履歴から生じた未完了作業は、新しい有効タスク・ブロッカー・判断待ちとしてCURRENTに反映されること。
- CURRENTから消えたタスクを後から追えるよう、履歴かGit等に参照可能な記録があること。
- 履歴は当時の状態を記録するもので、後に状況が変わっても全文を現在形へ書き換えない。現在の解釈・進捗はCURRENTを参照する。
- 過去の履歴に「未完了」「要確認」と記録されていても、現状の解決済みを意味するCURRENTと矛盾しない。時点が異なることが分かるようにする。

## 6. 文書境界と運用上の判断基準

### 6.1 記載先の判断

| 情報 | 正しい置き場所 |
|---|---|
| 「なぜこの機能を作るか」「今期のスコープ」 | PROJECT |
| 「どのコンポーネントが処理を確定するか」 | ARCHITECTURE |
| 「この機能はどのように振る舞うか」 | FUNC |
| 「入力項目・状態遷移・APIの詳細は何か」 | SPEC |
| 「この機能の実装は未着手で、次に何をするか」 | CURRENT |
| 「実装時に何を変更し、どこまでテストしたか」 | history（必要に応じてGit等を参照） |
| 「AIエージェントが実行・レビュー・更新をどう進めるか」 | AGENTS / ワークフロー |
| 「長く有効な意思決定の経緯」 | 決定記録・設計文書等の適切な正本。履歴から参照する |

STATUSに新しい仕様や技術方針が現れた場合、STATUSだけを唯一の正本にしない。必要な正本へ反映・参照する。ただし、未承認の案を正本に勝手に確定させない。

### 6.2 更新が必要な状態

次の変化を反映していないCURRENTは古い。

- 作業着手・中断・完了・中止、担当や優先順位の変更。
- 完了条件・依存関係・ブロッカーの追加や解消。
- 人間の判断・承認、外部審査・リリース等の実際の状態変化。
- 作業結果による新しいタスクや未確認事項の発生。
- フェーズ・マイルストーンの到達や対象範囲の変更。

履歴には、後から根拠を再確認する価値がある実施結果・判断の経緯が反映されている必要がある。ただし些細な途中経過をすべて記録することは要求しない。

### 6.3 確認できない状態の扱い

- AIが書いたコードは、実行・テストを確認するまで「実装済み・未検証」などと区別する。テスト成功と実機確認は別の事実として扱う。
- 人間が行う操作、外部サービスの状態、承認は、報告・証拠がなければ完了とみなさない。
- 記載同士が矛盾する場合は、推測で新しい正本を作らず、確認できる事実と未確認点を分ける。
- 日付や版番号、担当者を入力から確認できない場合は創作しない。
- 外部のCI・ストア・配布先などの状態が自動確認できない場合は、確認した時点と情報源を区別する。

### 6.4 更新の一貫性

- CURRENTを更新する際、冒頭サマリー、タスク本体、フェーズ一覧、ブロッカー、必要な履歴参照の整合が保たれること。
- 同じ事実をCURRENTと履歴の双方で独立した現在状態として更新し続けないこと。
- 履歴への分離を理由に、再開に不可欠な情報をCURRENTから消さないこと。
- CURRENTと履歴の更新が途中で不一致になった場合、どの記録が未更新か判断でき、回復可能であること。
- 作業上の更新タイミング・ツール利用・レビュー方法は本書で固定せず、必要な正しさを運用やワークフロー側で実現する。

## 7. 品質判定

### 7.1 品質観点（Q）

| ID | 観点 | 満たす状態 |
|---|---|---|
| Q1 | 現状の正確性 | CURRENTの現在位置・公開状態・タスク状態が、確認できる事実と一致する |
| Q2 | 次の作業の明確性 | 直近の着手先と完了条件が分かり、依存関係が必要な範囲で示される |
| Q3 | 完了の検証可能性 | 完了状態が検証済みの範囲を超えておらず、必要な根拠が追える |
| Q4 | 状態の一貫性 | 冒頭・タスク・フェーズ・ブロッカーで矛盾がない |
| Q5 | 再開への有用性 | 初見のAI/人間が1.3の問いに答えられる |
| Q6 | 正本・文書境界 | CURRENT、history、仕様等の正本が混ざり、判断を誤らせる状態でない |
| Q7 | 履歴の追跡可能性 | 重要な完了・中断作業の結果と検証範囲が、履歴や関連資料から辿れる |
| Q8 | 情報量の適切さ | CURRENTが履歴で埋もれず、必要な情報が省略されすぎてもいない |
| Q9 | 入力との整合 | 会話、提供資料、作業結果にない進捗・承認・検証を創作していない |

### 7.2 重大度と合否

**要修正**（作業の再開・優先順位・完了判断を誤らせる）:

- 完了していない作業、未実施の検証、未承認の判断が完了・確認済みとして記載されている。
- 冒頭の「次にやること」、タスク、フェーズ、ブロッカーが矛盾し、着手先を誤る。
- 重大なブロッカーや依存関係が欠け、安全・整合性・公開判断を誤る。
- 作業再開に不可欠な現在情報が履歴にしかなく、CURRENTから追跡もできない。
- 重要な実施結果・未解決事項が脱落し、現在位置の理解を誤る。
- 入力にない作業・判断・結果を捏造している。

**改善推奨**:

- 完了済みタスクの詳細がCURRENTに長く残る。
- 軽微な重複、冗長なログ、古い参照、読みにくいタスク粒度。
- 小さな作業の履歴が過剰に分割されている、または無関係な作業が一つに混ざっている。
- 履歴や完了結果の根拠への参照が弱いが、現状判断には重大な支障がない。

**参考**: 表現、見出し、表の見やすさなど。

**合否**: 要修正が0件であれば合格とする。点数化しない。未完了やブロッカーの存在を、それだけで不合格としない。

### 7.3 欠陥とみなさないもの

- 開発初期で、タスク数や履歴ファイル数が少ないこと。
- プロジェクトによって、フェーズやタスクの分け方が異なること。
- 未決定・調査中・人間の確認待ちがあること（正しく区別されている限り）。
- 関連する軽微な作業をまとめて1つの履歴としていること。
- GitやCI等の適切な記録を参照し、STATUSに生ログや詳細な差分を複製していないこと。

## 8. 本書が規定しない事項

本書は、タスクの実行順序、AIエージェントの内部手順、レビュー・修正ループ、更新を行うコマンド、Gitのブランチ運用、歴史ファイルの自動生成タイミングを固定しない。これらはプロジェクト固有の運用またはAGENTS・ワークフローが定める。

一方、どの方式を用いても、**現在状態の正確性、完了条件と検証結果の一致、履歴の追跡可能性、正本の分離、再開可能性**は満たさなければならない。
